Q1. Database Choice & Workload RDBMS (ACID)

Why Relational & Why Not NoSQL?

DocuVault manages court evidence, FIRs, and classified contracts where missing a single record or having partial writes invalidates legal trials.

• Engine: SQLite 3.x (WAL Mode) & PostgreSQL
• Access Pattern: ~80% Reads (Verification, Search) : 20% Writes (Atomic Uploads)
• Consistency: Strict Immediate Consistency (Serializable / Read Committed)
• Rejected: MongoDB (No native FK cascades, eventual consistency risk in clearance)
Q2. Schema & Relational Walkthrough 11 Normalized Tables

Entity Hierarchy & M:N Resolutions

Organizations ➔ Departments ➔ Positions ➔ Users ➔ Workspaces ➔ Documents ➔ Versions ➔ Signatures.

• 1:N: Workspaces ➔ Documents; Documents ➔ DocumentVersions
• M:N (Users ↔ DocumentVersions): Resolved via digital_signatures
• M:N (Users ↔ Workspaces): Resolved via temporary_clearances
• Referential Integrity: ON DELETE CASCADE (child versions) & SET NULL (actors)
Q3. Normal Forms & Denormalization 3NF / BCNF

Decomposition & Controlled Redundancy

Every determinant is a candidate key. Transitive dependencies eliminated (Users do not store Dept/Position names).

• 1NF: Atomic columns, surrogate primary keys, scalar serialization
• 2NF: No partial key dependencies; attributes depend on whole UUID PK
• 3NF: No transitive dependencies ($X \to Y \to Z$ removed)
• Deliberate Denormalization: audit_logs stores user name/position snapshot to prevent historical evidence tampering if an officer is later deleted!
Q4. Constraints & Transactions ★ Extra Credit Test

Data Correctness & Atomic Rollback

Document Upload executes inside a single ACID block: [Document] + [Version] + [Hash-Chained AuditLog].

• Constraints: NOT NULL, UNIQUE (email, doc_number, hash), FOREIGN KEYs
• Atomicity: If audit chaining fails, the document and version rollback
• Concurrency: SQLite WAL Mode allows concurrent readers alongside writer
• Extra Credit: Click button above to verify DB kernel rejecting duplicate keys!
Q5. Indexing & 100x Scaling B-Tree Indexes

Execution Plans & Scale Strategy

B-Tree index on sha256_hash provides $O(\log N)$ logarithmic verification instead of $O(N)$ full table scans.

• Active Indexes: sha256_hash, sequence_number, email, workspace_id
• Rejected: details_json (write amplification) & booleans (low cardinality)
• 100x Growth Plan: Range partitioning on audit_logs by year, read replicas for search queries, blob decoupling to S3/GCS.
