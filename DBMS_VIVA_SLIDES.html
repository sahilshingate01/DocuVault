Question 1 (0:45 – 2:15)

Why Did You Choose This Database?

Relational RDBMS with ACID vs Document Store Evaluation

Database Architecture

  • Type: Relational Database Management System (RDBMS)
  • Engines: SQLite 3.x with WAL Mode (Edge Vault) & PostgreSQL (Enterprise)
  • Data Shape: Structured multi-tenant hierarchy (Orgs ➔ Depts ➔ Positions ➔ Users ➔ Workspaces ➔ Documents ➔ Versions ➔ Signatures)
  • Read/Write Ratio: ~80% Reads (Verification, Search) : 20% Writes (Atomic Uploads)

Consistency & Rejected Alternative

  • Consistency: Strict Immediate Consistency (Serializable / Read Committed). Eventual consistency is unacceptable in criminal evidence.
  • Rejected Alternative: MongoDB / NoSQL Document Store
  • Why Rejected: No native cascading foreign keys; eventual consistency risks clearance leaks; lack of hardware-guaranteed hash-chain ordering across separate collections without heavy two-phase commits.
▶ Spoken Script & Screen Action:
"For DocuVault, we chose a Relational Database Management System (RDBMS), specifically SQLite 3 with Write-Ahead Logging and PostgreSQL. Our data is highly structured and relational. As you can see on screen in our table inventory, our workload is read-heavy: roughly 80% reads and 20% writes. We require strict immediate consistency with ACID guarantees. In court evidence, eventual consistency is unacceptable. We considered MongoDB, but rejected it because it lacks native cascading foreign keys and cannot guarantee ordered hash-chain serialization across collections without heavy two-phase commit overhead."

Question 3 (4:00 – 5:30)

Normal Forms & Controlled Denormalization

3NF / BCNF Decomposition Proofs & Audit Log Historical Snapshot

Normalization Decomposition

  • 1NF: Unique surrogate UUID keys; atomic scalar attributes; no repeating groups.
  • 2NF: 1NF + zero partial key dependencies on UUID keys.
  • 3NF: 2NF + zero transitive dependencies ($X \to Y \to Z$ removed; Users store position_id, not position title).
  • BCNF: In documents, all determinants (id, document_number) are candidate keys.

Controlled Denormalization

  • Table: audit_logs stores user_name, user_email, user_position alongside user_id.
  • Why: Forensic non-repudiation! If an officer changes rank or is deleted 5 years later, a dynamic join would corrupt historical court evidence!
  • Maintenance: Audit log is strictly append-only; snapshot is sealed inside the SHA-256 block upon insertion.
▶ Spoken Script:
"Our design reaches Third Normal Form (3NF) and BCNF. All attributes are atomic, and by using single-column surrogate UUIDs, we eliminate all partial dependencies. Transitive dependencies are removed: the Users table stores position_id and department_id rather than department names. We deliberately introduced controlled denormalization in our audit_logs table by storing snapshots of user names and positions alongside user_id. Why? Because in a court inquiry years later, if an employee is deleted or reassigned, a dynamic join would corrupt historical evidence! Correctness is maintained because audit logs are strictly append-only and sealed in the SHA-256 chain."

Data Correctness, Constraints & Transactions

ACID Atomic Pipeline & Live Constraint Rejection (Extra Credit)

Integrity Constraints

  • NOT NULL: document_number, sha256_hash, email, entry_hash
  • UNIQUE: documents.document_number, users.email, workspaces.code
  • Database vs App Division: Database enforces referential integrity and uniqueness; Application enforces Bell-LaPadula clearance rules and RSA cryptographic signatures.

Atomic Transactions & Extra Credit

  • Atomic Pipeline: Upload commits [Document] + [Version] + [AuditLog] simultaneously.
  • Rollback Safety: If audit chaining fails, the entire transaction rolls back with 0 orphaned records.
  • EXTRA CREDIT DEMO: Triggering duplicate document_number produces UNIQUE constraint failed exception caught live!

Question 5 (7:15 – 9:00)

Database Efficiency, Indexes & 100x Scaling Strategy

B-Tree Indexes, EXPLAIN QUERY PLAN & Enterprise Scale Architecture

Indexes Created & Rejected

  • Active B-Tree Indexes:
    • ix_document_versions_sha256_hash ($O(\log N)$ file verification)
    • ix_documents_workspace_id & classification
    • ix_audit_logs_sequence_number & entry_hash
  • Rejected Indexes:
    • details_json (high write amplification on every action)
    • is_deleted (low cardinality; 2 values cause optimizer to use table scan)

100x Scaling Strategy

  • Range Partitioning: Partition audit_logs by year and month.
  • Read Replicas: Primary database for writes and hash-chaining; streaming read replicas for clearance queries.
  • Blob Decoupling: Store raw files in S3 / GCS, keeping only SHA-256 fingerprint pointers in DB.
  • Redis In-Memory Caching: Cache clearance tiers and session tokens with invalidation hooks.
